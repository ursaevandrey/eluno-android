# Архитектура Eluno для Android

Обновлено: 1 ноября 2026 года. Реализованы Compose UI, Matter-адаптер и два App Widget с конфигуратором. Документ описывает целевую архитектуру; полная аппаратная приёмка, постоянная очередь с claim/lease и удаление fabric с устройства остаются открытыми. Текущие границы и сборка Matter описаны в `MATTER.md`.

## 1. Задача и границы

Eluno — самостоятельное Android-приложение для локального управления Matter-устройствами. Пользователь может подключить устройство, управлять его доступными функциями и добавить виджет конкретного устройства на рабочий стол.

Подтверждено пользователем:

- Kotlin и Jetpack Compose.
- Независимое локальное управление, без привязки к Google Home.
- Типы устройств: розетка, лампа, светодиодная лента; архитектура допускает другие типы.
- Виджеты для управления конкретным устройством.
- Актуальные версии зависимостей.
- Compose UI реализован по выбранному прототипу, включая светлую/тёмную темы и адаптивную Fold-компоновку.
- Thread пока не поддерживается.

В этом документе «без Thread» означает Matter over Wi-Fi/Ethernet. Matter — протокол прикладного уровня поверх IP; Thread — один из возможных сетевых транспортов. BLE используется для первичного подключения, а не для повседневного управления. [Matter Primer](https://developers.home.google.com/matter/primer)

Предлагаемые границы первой версии, которые можно уточнить отдельно:

- Один локальный дом и один телефон-контроллер; модель данных не ограничивает дальнейшее добавление домов.
- Работа в доступной локальной IPv6-сети, включая сеть без доступа в интернет.
- Без собственного сервера, обязательного аккаунта, облачной синхронизации, удалённого доступа и фоновых автоматизаций.
- Минимальная версия Android — 9, API 28. Это продуктовый выбор для сокращения матрицы поддержки, а не требование самого Matter.
- Последние **стабильные совместимые** зависимости; preview-версии не подключаются автоматически.
- Поддержка сертифицированных Matter-устройств с реализованными стандартными возможностями. Наличие логотипа Matter не означает поддержку приложением всех функций устройства.

## 2. Основное решение

Использовать модульный монолит с чистым Kotlin-ядром, репозиториями, отдельным адаптером Matter SDK и двумя независимыми потребителями бизнес-логики: Compose-экранами и Android App Widgets.

Бизнес-логика не зависит от Activity, ViewModel, Glance, Room или классов Matter SDK. Экран и виджет отправляют одинаковые команды через один сценарий управления. Подтверждённые сведения хранятся локально и доступны после перезапуска процесса.

Логическая структура:

```text
Compose-экраны → ViewModel ─┐
                           ├→ сценарии domain → интерфейсы репозиториев
Glance → callback / worker ┘                          ↑ реализует
                                                   data
                                                  /    \
                                             database  matter
                                                          ↓
                                                    Matter SDK
                                                          ↓
                                               Wi-Fi / Ethernet
```

Стрелки к интерфейсам показывают обращения; реализации подставляются при сборке приложения. Domain не импортирует data. UI и виджеты не обращаются напрямую к SDK или DAO.

Не создавать отдельный сервис, микросервис или Gradle-модуль для каждого типа устройства. Типы отличаются набором возможностей и профилем представления.

## 3. Модули и зависимости

| Модуль | Ответственность | Зависимости внутри проекта |
|---|---|---|
| `:app` | Application, сборка графа объектов, Android entry points, типизированная Compose-навигация | domain, data, matter, database, widgets и feature-модули |
| `:core:designsystem` | Общие светлая/тёмная схемы, типографика, формы и базовые Compose-компоненты Eluno | Compose Material 3 |
| `:core:domain` | Модели, возможности, команды, сценарии, контракты репозиториев и Matter-порта | Нет Android-модулей |
| `:core:data` | Реализации репозиториев, согласование состояния, журнал команд, координация подписок | domain, database |
| `:core:database` | Room, DAO, сущности и миграции; локальные настройки через DataStore | Не зависит от feature-модулей |
| `:core:chip` | Закреплённые bindings, JNI и PAA connectedhomeip | Внешний SDK |
| `:core:matter` | Реализация Matter-порта: commissioning, discovery, сессии, чтение, команды, подписки, защищённое хранилище SDK | domain, внешний Matter SDK |
| `:feature:widgets` | Привязки виджетов, Glance entry points, обработчики, worker и обновление RemoteViews | domain |
| `:feature:devices` | Список, детали устройства и их ViewModel | domain |
| `:feature:commissioning` | Подключение реальных устройств Matter | domain |
| `:feature:settings` | Тема, динамические цвета и информация о приложении | domain |

Внутри domain разделить пакеты `model`, `capability`, `command`, `repository`, `port`, `usecase`. Если размер проекта вырастет, выделить model и контракты в отдельные модули; сейчас это избыточно.

`feature`-модули зависят от domain и `:core:designsystem`, получают реализации контрактов через constructor injection. Палитры определены явно; динамические системные цвета применяются только по настройке пользователя на поддерживаемых версиях Android.

На старте — constructor injection и небольшой `AppContainer` в `:app`, с фабриками ViewModel/Worker и доступом из Android entry points. Глобальный service locator не используется в бизнес-коде. Это позволяет начать без отдельного DI-фреймворка; при росте графа его можно заменить на Hilt без изменения domain.

## 4. Matter-контроллер

### 4.1. Основа

Использовать официальный открытый SDK `project-chip/connectedhomeip`, его Android/JVM bindings и нативную библиотеку. Собственный Kotlin-адаптер скрывает JNI, SDK callback-и, raw cluster ID и особенности жизненного цикла.

Google Home APIs и Google Play services не входят в обязательный путь подключения и управления. Собственная fabric — доверенная область Eluno с собственными операционными сертификатами и ключами. Подключение к Google fabric само по себе не предоставляет приложению прямого доступа к устройству; поэтому Google commissioning не используется как замена собственному контроллеру. [Home Mobile SDK](https://developers.home.google.com/matter/apis/home)

SDK берётся из конкретного release tag, с фиксацией commit SHA, submodules и инструментов нативной сборки. Не использовать плавающий `master`. Версию Android bindings и native-библиотек обновлять вместе. Android CHIPTool служит техническим примером, а не готовой продуктовой архитектурой. [Релизы SDK](https://github.com/project-chip/connectedhomeip/releases), [Android CHIPTool](https://github.com/project-chip/connectedhomeip/tree/master/examples/android/CHIPTool)

### 4.2. Компоненты адаптера

| Компонент | Назначение |
|---|---|
| `MatterRuntime` | Ленивая инициализация SDK, native event loop, освобождение ресурсов |
| `FabricStore` | Сохранение identity контроллера, сертификатов и состояния fabric |
| `CommissioningCoordinator` | Управляемая последовательность подключения и обработка частичных ошибок |
| `OperationalDiscovery` | Поиск уже подключённых узлов через DNS-SD/mDNS, актуальные адреса |
| `SessionManager` | CASE-сессии и повторное установление соединения |
| `EndpointInspector` | Descriptor, endpoint topology, поддерживаемые clusters/attributes/features |
| `ClusterAdapter` | Преобразование доменных команд и значений в операции SDK |
| `SubscriptionManager` | Подписки на атрибуты, повторное подключение, освобождение подписок |

Runtime один на процесс; компоненты не создают конкурирующие native-контроллеры для экрана и виджета. Сетевые и JNI-операции выполняются вне главного потока. Отмена coroutine должна отменять операцию SDK либо делать её поздний callback безопасным; одного `withTimeout` вокруг блокирующего вызова недостаточно.

### 4.3. Подключение устройства

Состояния сценария:

```text
Idle → ValidatingPayload → Discovering → EstablishingPase
     → VerifyingAttestation → ProvisioningNetworkIfNeeded
     → InstallingFabricCredentials → EstablishingCase
     → CompletingCommissioning → InspectingEndpoints → Ready

На каждом шаге возможны Failed или Cancelled.
```

Это доменные стадии, а не точная копия порядка callback-ов SDK. Детальные операции и fail-safe реализует SDK по протоколу. [Matter commissioning](https://developers.home.google.com/matter/primer/commissioning)

1. Получить QR/manual onboarding payload; валидировать формат. В форме подключения доступен встроенный QR-сканер ZXing с запросом CAMERA по нажатию; распознанный код подставляется в форму без автоматического pairing.
2. Проверить разрешения и доступность Bluetooth/локальной сети. Отклонить Thread-only onboarding с понятной причиной.
3. Создать защищённую PASE-сессию и проверить attestation, без отключения проверки в production.
4. Для нового Wi-Fi-устройства передать сетевые параметры через защищённую сессию. Ethernet обычно уже имеет сетевое подключение. Пароль Wi-Fi не хранить после завершения/отмены сценария.
5. Добавить устройство в fabric Eluno, установить операционную CASE-сессию и завершить commissioning.
6. Прочитать структуру endpoints и их возможности, сохранить устройство и выполнить начальное чтение состояния.

Незавершённые подключения не сохранять по решению пользователя. Каталог записывается только после успешного чтения Descriptor. Если предыдущая попытка уже добавила fabric, повторное явное добавление с новым кодом распознаёт существующий доступ по совпадению fabric ID и root public key, затем подтверждает его через CASE.

После прерывания процесса не восстанавливать попытку добавления автоматически. Сохранять ключи fabric и уже готовые устройства; учитывать fail-safe и возможность частичного завершения на устройстве.

Предусмотреть multi-admin onboarding устройств, уже добавленных в другую экосистему: пользователь открывает commissioning window существующим администратором и передаёт новый код Eluno. Исходный QR не гарантирует повторное добавление. Поддержка устройств за Thread-сетью этим путём также не входит в первую версию.

### 4.4. Сеть

- Сохранять идентичность узла, а не IP-адрес как его основной идентификатор.
- Проверять IPv6-доступность, mDNS и выбранный интерфейс. Смена Wi-Fi, VPN или адреса требует повторного discovery/сессии.
- Наличие интернета и системный признак validated network не требуются для локального управления.
- Не считать любую доступную Wi-Fi-сеть домашней сетью пользователя. Доступность конкретного узла подтверждается discovery/сессией.
- При уходе из локальной сети показывать отсутствие доступа. Облачного fallback в первой версии нет.

## 5. Модель устройств: идентичность, тип и возможности

Matter-узел может иметь несколько endpoints, а каждый endpoint — несколько clusters. Поэтому один физический прибор не всегда равен одному управляемому объекту. [Модель данных Matter](https://developers.home.google.com/matter/primer/device-data-model)

### 5.1. Основные сущности

| Сущность | Назначение |
|---|---|
| `Home` | Локальная логическая группа; не равна fabric |
| `FabricRef` | Стабильный внутренний ID fabric; ссылки на её защищённое хранилище |
| `MatterNode` | Узел, адресуемый парой `FabricRef + NodeId` |
| `MatterEndpoint` | Endpoint внутри узла, raw device types, topology, обнаруженные возможности |
| `Device` | Пользовательский управляемый объект со стабильным UUID, названием и категорией |
| `DeviceBinding` | Связь Device с узлом и endpoint; явный основной endpoint управления |
| `CapabilityDescriptor` | Поддерживаемая возможность, ограничения, доступные режимы и адрес назначения |
| `DeviceSnapshot` | Последние известные значения атрибутов, время и качество данных |
| `CommandRecord` | Запрос, целевое значение, стадия, deadline, результат и причина ошибки |
| `WidgetBinding` | `appWidgetId → DeviceId`, настройки и выбранные действия |

В MVP один Device представляет один управляемый endpoint. Многоканальная розетка становится несколькими Device, объединёнными общей ссылкой на MatterNode. Endpoint 0 с административными функциями не превращается в обычное устройство управления. Произвольные bridge-топологии можно сохранять, но их полная продуктовая поддержка не обещается в MVP.

64-битные NodeId хранить без потери unsigned-диапазона, например фиксированной hex-строкой или 8-байтным BLOB, с преобразованием внутри адаптера. Fabric index SDK не использовать как постоянный ID приложения. После factory reset и нового commissioning не перепривязывать виджеты автоматически к новому узлу.

### 5.2. Пользовательские категории

`DeviceKind`: `Outlet`, `Light`, `LightStrip`, `Unknown`.

Категория помогает выбрать имя, значок и будущий набор элементов управления. Она не определяет допустимость команды. Светодиодная лента может объявлять тот же Matter lighting device type, что и лампа; пользовательское уточнение категории хранится отдельно от данных протокола.

### 5.3. Возможности

| Возможность | Доменные операции | Как обнаруживается |
|---|---|---|
| `OnOff` | `SetPower(on)` | On/Off server cluster и поддерживаемые команды |
| `LevelControl` | `SetBrightness(percent, transition)` | Level Control, features, ограничения уровня |
| `ColorTemperature` | `SetColorTemperature(kelvin, transition)` | Color Control и поддержка температуры с min/max |
| `ColorControl` | `SetColor(color, transition)` | Color Control, конкретные режимы hue/saturation и/или xy |
| `PowerMeasurement` | Наблюдение измерений | Опциональные measurement clusters; расширение после MVP |

Розетка может иметь только OnOff. Лампа может иметь OnOff + LevelControl. Лента может дополнительно поддерживать цвет и температуру. Нельзя обещать яркость для любой лампы или цвет для любой ленты.

Возможности определяются по Descriptor, server clusters, FeatureMap, спискам атрибутов/команд и ограничениям устройства. Неподдерживаемая операция возвращает `UnsupportedCapability` до отправки в сеть. Неизвестные clusters сохраняются для диагностики и не ломают остальные функции.

В domain используются нормализованные единицы: проценты, kelvin, типизированные модели цвета. Адаптер выполняет преобразование в протокольные значения, учитывает диапазоны и nullable/unknown значения. Для яркости явно определить поведение нулевого значения и команды с изменением питания; не полагаться на неявные эффекты `MoveToLevel`.

## 6. Состояние и управление командами

### 6.1. Источники данных

Физическое устройство — источник фактического состояния. Локальная БД — единый источник наблюдаемой модели приложения и виджетов. SDK reports и результаты чтения попадают в репозиторий, затем в БД и `Flow`; потребители не получают конкурирующие независимые состояния напрямую из SDK.

Хранить отдельно:

- **Reported state:** последнее полученное значение каждого атрибута.
- **Freshness:** `Unknown`, `Fresh`, `Stale`, время наблюдения и источник.
- **Availability:** `Unknown`, `Reachable`, `Unreachable`; отдельно причина недоступности.
- **Pending command:** желаемое значение, ID команды, стадия и deadline.

`false` не заменяет неизвестное значение, а истечение срока свежести не означает, что устройство выключено. Freshness оценивается по атрибутам и активности подписки. После перезапуска без подтверждённой связи кеш не объявляется актуальным автоматически.

### 6.2. Контракты domain

Контракты ниже описывают границы, а не являются готовым исходным кодом:

```kotlin
interface DeviceRepository {
    fun observeDevices(homeId: HomeId): Flow<List<Device>>
    fun observeSnapshot(deviceId: DeviceId): Flow<DeviceSnapshot>
    suspend fun refresh(deviceId: DeviceId): RefreshResult
}

interface DeviceCommandRepository {
    suspend fun submit(request: CommandRequest): CommandId
    fun observe(commandId: CommandId): Flow<CommandStatus>
}

interface MatterPort {
    suspend fun inspect(node: NodeAddress): NodeDescriptor
    suspend fun read(target: AttributeTarget): AttributeReport
    suspend fun execute(command: MatterOperation): OperationResult
    fun subscribe(targets: Set<AttributeTarget>): Flow<AttributeReport>
}
```

Commissioning и управление fabric имеют отдельные порты: они требуют другого жизненного цикла, чем обычное чтение/управление. Android permissions и запуск Activity остаются в платформенных entry points.

Ключевые use cases: `CommissionDevice`, `InspectDevice`, `ObserveDevices`, `ObserveDeviceState`, `SetDevicePower`, `SetDeviceBrightness`, `SetDeviceColor`, `RefreshDevice`, `BindWidget`, `RemoveDevice`.

### 6.3. Выполнение команды

Текущая реализация: общий `DeviceRepository` последовательно исполняет команды каждого endpoint под mutex. Срок 15 секунд включает ожидание очереди, чтение для переключателя, отправку и подтверждение. Worker дополнительно учитывает время от входа в callback виджета; просроченный запрос не отправляется. Переключатель читает фактическое питание внутри той же очереди и отправляет абсолютный `SetPower`. Pending/Running записываются транзакционно, отмена очищает pending по ID, после process death команда не переотправляется. Описанная ниже постоянная очередь с claim/lease и расширенными статусами пока является целевой моделью.

1. Проверить наличие устройства, привязку endpoint, возможности и параметры.
2. Сохранить запрос с `commandId`, порядковым номером и deadline в БД.
3. Получить право исполнения через атомарный claim записи. Живой процесс исполняет сразу; после восстановления применяется тот же исполнитель.
4. Установить сессию, отправить команду, записать транспортный результат.
5. Получить подтверждённое состояние через report или read-back; снять pending.
6. Обновить все виджеты, привязанные к Device.

Статусы: `Queued`, `Running`, `Acknowledged`, `Confirmed`, `Failed`, `Expired`, `OutcomeUnknown`, `Superseded`. Ответ SDK об успешной команде не всегда подтверждает физическое состояние, особенно при переходе яркости/цвета. Время перехода учитывается в ожидании результата.

Разделять подтверждение выполнения протоколом и совпадение наблюдаемого состояния с целевым: другие контроллеры могут успеть изменить устройство. Reports не несут ID команды Eluno; совпадение значения не доказывает, какой контроллер его установил.

Политика очереди:

- Последовательное исполнение для одного endpoint; независимые endpoints могут работать параллельно с общим ограничением нагрузки.
- Для ещё не отправленных изменений одного свойства разрешено объединение в последнее значение. Учитывать связанные операции питания/яркости, чтобы не нарушить порядок.
- Использовать абсолютные команды `SetPower(true/false)`. Повтор `Toggle` после таймаута может вернуть устройство в исходное состояние, поэтому автоматические повторы Toggle запрещены.
- Повторять лишь временные ошибки и только в пределах deadline; не повторять permission/auth/unsupported ошибки.
- После неоднозначного исхода сначала прочитать состояние. Не обещать exactly-once для физического устройства; локальная дедупликация не устраняет сбой между отправкой и записью результата.
- Старые команды не должны включать прибор после возвращения пользователя домой. Начальная проектная граница — 15 секунд от нажатия до истечения запроса; уточнить измерениями на устройствах. Это не гарантия времени выполнения Android.

Транзакцию Room нельзя держать открытой во время сетевого вызова. Для захвата исполнения использовать lease/owner; после process death истёкший lease восстанавливается с проверкой исхода. Восстановление никогда не отправляет запрос после deadline.

### 6.4. Подписки

Текущая реализация: foreground-координатор владеет подписками каталога и опросом раз в 15 секунд после предыдущего ответа. Через две секунды в фоне он отменяет работу и дожидается её завершения перед новым запуском. Общий кэш атрибутов объединяет read, read-back и partial reports с учётом cluster data version; последовательность наблюдений защищает запись в Room от поздней доставки. Время подтверждения хранится по атрибутам в адаптере, в Room сохраняется самое старое из этих времён, чтобы частичный отчёт не освежал остальные значения.

Подписываться на состояния устройств, за которыми сейчас наблюдает приложение. Отдельный координатор считает потребителей, объединяет одинаковые подписки и освобождает их при отсутствии спроса. После обрыва — повторное подключение с backoff и jitter, затем актуализация состояния.

Не держать постоянную подписку только потому, что на рабочем столе существует виджет. Пока процесс активен, новые reports могут обновлять и виджеты; после его выгрузки они показывают сохранённые сведения.

## 7. Виджеты устройств

Использовать Jetpack Glance для Android App Widgets. Это отдельный слой представления с Compose-подобным API и ограничениями RemoteViews; переиспользовать обычные Compose-экраны в виджетах не планируется.

Один экземпляр виджета привязан к конкретному Device. На одно устройство можно создать несколько виджетов. Реализованы вертикальный и горизонтальный варианты, переключатель питания и переход в приложение; дополнительные действия яркости/цвета остаются будущим расширением. Разметка и визуальные требования описаны в [руководстве по реализации дизайна](design/ANDROID_IMPLEMENTATION_GUIDE.md).

`feature:widgets` содержит модель представления, вычисление изменений и сценарий переключения; Android entry points и Glance-renderer собираются в `app`. Привязки доступны только через доменный `WidgetBindingRepository`, его реализация находится в `core:data`; прямого доступа renderer/configurator/worker к DAO нет.

Состояние хранится вне памяти виджета: привязки в Room, общие настройки приложения в DataStore. Launcher отображает RemoteViews в своём процессе, а callbacks и workers Eluno запускаются в процессе приложения. Отдельный `android:process` для widgets не добавлять. [Состояние GlanceAppWidget](https://developer.android.com/develop/ui/compose/glance/glance-app-widget)

### 7.1. Действие пользователя

Сейчас callback ставит один expedited `OneTimeWorkRequest` с обычным fallback и сроком 15 секунд. Worker повторно проверяет привязку/разрешение и вызывает общий атомарный сценарий переключения. Автоматического retry нет, незавершённые команды после перезапуска не отправляются. Следующая схема описывает будущую постоянную очередь, а не уже работающий claim-механизм:

```text
Нажатие → ActionCallback → запись команды в БД
        → короткая попытка общего исполнителя
        → при необходимости OneTimeWorkRequest для незавершённой команды
        → проверка deadline и claim → Matter → report/read-back
        → сохранение результата → обновление всех связанных виджетов
```

Callback не запускает бесконтрольную coroutine и не хранит единственную копию команды. Для продолжения за пределами короткого callback используется WorkManager; worker может запросить expedited execution с обычным fallback. Это ускорение по возможности, не гарантия немедленного старта. [Действия Glance](https://developer.android.com/develop/ui/compose/glance/user-interaction), [Work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

Запись команды и постановка WorkManager не являются одной транзакцией. При старте приложения/новом действии reconciliation находит неистёкшие незавершённые команды и восстанавливает обработку; истёкшие помечает без отправки. Все исполнители используют один claim-механизм, чтобы callback и worker не отправили запрос одновременно.

Если кеш питания устарел, не вычислять скрытое Toggle по нему. Предпочтительны явные действия «включить»/«выключить»; если позже выбран один переключатель, сначала потребуется актуальное чтение. В параметрах действия передаются только идентификаторы и безопасные значения, не ключи fabric и не QR-коды.

При отсутствии разрешения или необходимости разблокировки виджет показывает состояние, требующее открытия приложения. Переход выполняется прямым `actionStartActivity`, без запуска Activity через receiver/worker. Действие заново проверяет привязку, Device и разрешения, даже если RemoteViews устарели.

### 7.2. Обновление и жизненный цикл

- После команды, чтения и report обновлять только экземпляры с изменившимся отображаемым содержимым. Текущая реализация сравнивает `WidgetPresentation`; изменения одного времени подтверждения не запускают RemoteViews update. Без привязок наблюдение состояний для виджетов не создаётся.
- При системном обновлении, создании и восстановлении — построить представление из БД; сеть запускается отдельно и ограниченно.
- Текущий виджет показывает имя, иконку и доступность действия с pending. Питание не кодируется цветом кнопки, время подтверждения и ошибки остаются в приложении; их отображение в виджете — отдельное будущее расширение. Кеш не выдаётся за непрерывное наблюдение.
- Периодический опрос по умолчанию выключен. Если понадобится, WorkManager допускает минимальный период 15 минут, а реальный запуск зависит от ОС; секундное фоновое обновление не обещается. [Периодическая работа](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)
- Смерть процесса не удаляет привязки. Force stop, Doze, ограничения производителя и перезагрузка входят в отдельные проверки; непрерывная работа при них не гарантируется.
- До первого разблокирования после перезагрузки управление недоступно: fabric хранится в credential-protected storage.
- `onDeleted` удаляет привязку виджета, но не устройство. Удаление устройства инвалидирует все его виджеты.
- При восстановлении `appWidgetId` заново сопоставляется через механизм restore; перенос виджета не восстанавливает утраченные ключи fabric.

Не применять постоянный foreground service для поддержания «живого» виджета. `NetworkType.CONNECTED` не доказывает доступность Matter-узла и может быть неподходящим фильтром для локальной сети без интернета; доступ проверяется самим адаптером и deadline.

## 8. Хранение и безопасность

Room хранит `homes`, `fabrics_metadata`, `nodes`, `endpoints`, `devices`, `device_bindings`, `capabilities`, `attribute_snapshots`, `command_records`, `widget_bindings`. Версии схем и миграции фиксируются в репозитории; destructive migration в production запрещена.

DataStore используется для небольших настроек: выбранный дом, предпочтения приложения, будущая тема. Связанные сущности и журнал команд остаются в Room. Журнал имеет ограниченный срок хранения; очищаются завершённые записи, а не незавершённые операции без разбора.

Реализованная политика журнала: завершённые записи старше 30 дней или за пределами последних 1000 удаляются порциями до 200. При запуске выполняется до пяти порций, после команды — одна. Активные записи и записи с действующим pending исключаются; накопившийся до обновления большой журнал сокращается постепенно.

Ключи fabric, operational private keys и секреты SDK не хранить в обычных Room-таблицах, логах, параметрах Intent и WorkManager Data. `FabricStore` использует Android Keystore для защиты ключа шифрования и шифруемое приватное хранилище SDK. Возможность прямого использования неэкспортируемого ключа Keystore через SDK требует проверки; её нельзя предполагать без реализации crypto delegate.

Исключить секреты и зависимые от них идентификаторы/привязки из Auto Backup и переноса между устройствами. MVP не восстанавливает fabric на другом телефоне. После удаления приложения доступ может потребовать повторного multi-admin onboarding или сброса устройства, если другого администратора нет. Обычный экспорт списка устройств не восстанавливает право управления.

Для production нужен собственный lifecycle операционных credentials и проверка attestation с поддерживаемым набором доверенных PAA. Не переносить общие ключи и development fabric из примеров. Политика обновления trust store должна сохранять локальное управление при отсутствии интернета; получение обновлений доверенных корней не является облачным управлением устройствами. Google отдельно предупреждает, что sample development fabric не предназначена для production. [Matter sample codelab](https://developers.home.google.com/codelabs/matter-sample-app)

Удаление разделить на две операции:

- Удалить доступ Eluno: запросить `RemoveFabric` только для собственной fabric; затем очистить локальные данные.
- Забыть локальную запись недоступного узла: объяснить, что удалённое устройство может сохранить fabric. Не выдавать эту операцию за отзыв доступа на устройстве.

Не выполнять factory reset устройства для обычного удаления и не затрагивать fabric других экосистем.

## 9. Разрешения и Android-ограничения

Минимальный набор уточняется по используемым API:

- `INTERNET`, `ACCESS_NETWORK_STATE` для сетевого взаимодействия и диагностики.
- На Android 12+ — runtime `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` при BLE commissioning; на поддерживаемых старых Android учитывать требования BLE discovery к location permissions.
- Camera — только при использовании собственного QR-сканера; ручной код не требует камеры.
- Wi-Fi permissions — только если выбранные сетевые API действительно их требуют, с проверками по API level.
- На Android 17 при target API 37 — `ACCESS_LOCAL_NETWORK` для необходимого доступа к локальным устройствам. Отсутствие разрешения должно выявляться до попытки сетевой команды. [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)

Разрешения запрашиваются по сценарию, а не все при первом запуске. Работа виджета после первичной настройки не должна требовать повторного ввода credentials. Если право отозвано, worker завершает запрос с типизированной ошибкой и не открывает диалог разрешений сам.

## 11. Проверки будущей реализации

### Domain и data

- Возможности обнаруживаются независимо от пользовательской категории; неподдерживаемые команды не отправляются.
- Две розетки одного узла имеют независимые endpoint bindings и состояния.
- Unknown/stale не превращаются в `off`; reported state не затирается желаемым значением.
- Одновременные действия из приложения и нескольких виджетов сохраняют порядок.
- Повторы, deadline, superseded-команды и восстановление lease не отправляют устаревшие запросы.
- Сбой после отправки, но до записи результата приводит к проверке состояния, а не слепому повтору.
- Room migrations и удаление устройства корректно обновляют связанные данные и виджеты.

### Matter-интеграция

Реальные Wi-Fi/Ethernet-устройства: розетка, диммируемая лампа, цветная лампа/лента; желательно более одного производителя. Проверить commissioning, перезапуск приложения, power cycle устройства, read/write/subscribe, смену IP, недоступность mDNS и работу LAN без интернета. Эмулятор/fake не заменяет проверку BLE, IPv6 и native SDK.

### Android и виджеты

Проверить на минимальной и актуальной версиях Android, в том числе на физическом телефоне: cold start по нажатию виджета, process death, Doze, отказ в разрешениях, ограничения батареи, reboot и первое разблокирование, удаление/восстановление виджета. Force stop проверяется отдельно от обычной смерти процесса.

Измерять время от нажатия до protocol acknowledgement и подтверждённого состояния отдельно; учитывать холодную и тёплую сессию. Логировать только технические стадии, обезличенные correlation ID и длительности, без сетевых паролей, onboarding payload и приватных ключей.

## 12. Порядок реализации

1. **Проверка Matter SDK:** собрать выбранный Android SDK, проверить ABI/размер страницы 16 KB, собственное защищённое хранение fabric, подключение Wi-Fi-розетки и управление после перезапуска. Отдельно подтвердить рабочий путь attestation. Это главный технический риск до UI.
2. **Каркас:** Gradle-модули, version catalog, domain, fake Matter-порт и базовая проверка сборки/границ зависимостей.
3. **Локальные данные:** Room, миграции, каталог возможностей, snapshots, журнал команд и восстановление после сбоев.
4. **Реальный контроллер:** commissioning, endpoint inspection, команды OnOff, чтение и подписки; обработка LAN без интернета.
5. **Виджеты:** постоянные привязки и исполнение команд после cold start. Реализация разметки — отдельный будущий этап UI.
6. **Освещение:** яркость, температура, цвет и тестирование частично поддерживаемых возможностей.
7. **Интерфейс приложения:** выбранный прототип перенесён в Compose; остаётся нативная визуальная проверка на телефоне/AVD и Fold-профиле.

Критерий готовности технической основы: устройство подключается к собственной fabric Eluno; приложение и виджет используют общий командный путь; после перезапуска доступ восстанавливается; недоступность сети и истёкшие команды не приводят к ложному подтверждению или позднему включению устройства.

## 13. Решения, которые можно уточнить позже

Не блокируют текущую архитектуру:

- Подтвердить минимальную Android 9 или расширить поддержку старых устройств.
- Нужны ли несколько домов и комнаты уже в первой версии.
- Какой конкретный набор устройств доступен для интеграционных проверок.
- Какие действия доступны непосредственно в виджете помимо питания.
- Нужен ли перенос доступа на второй телефон; это отдельная задача управления credentials, а не копирование Room.

Thread исключён из первой версии по явному решению пользователя. Если понадобится позже, отдельно проектируются commissioning, доступ к Thread credentials и работа через Border Router; текущая задача этого не включает.
